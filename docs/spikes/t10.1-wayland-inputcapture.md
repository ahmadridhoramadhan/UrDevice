# Spike T10.1: Wayland InputCapture portal (GNOME and KDE)

Date: 20 November 2026. Result: **GNOME 45+ and KDE Plasma 6.1+ can share their mouse** through `org.freedesktop.portal.InputCapture` and libei. wlroots compositors (Sway, Hyprland, Wayfire) have no such portal, so a desktop there can be controlled but needs a different capture path. The GNOME end-to-end test was **not completed here** because the permission dialog could not be answered unattended (details below).

## Question

Design §18.3 plans to capture the physical mouse and keyboard on Wayland with `org.freedesktop.portal.InputCapture` and libei. Which desktops implement it, and what does the flow cost the user?

## What was tried

| Item | Value |
|---|---|
| Machine | Ubuntu, GNOME Shell 50.1 on Wayland, `xdg-desktop-portal` 1.21.1, `xdg-desktop-portal-gnome` 50.0, `libei1` and `libeis1` 1.5.0 |
| Probe | [`probes/t10_1_inputcapture.py`](probes/t10_1_inputcapture.py): a host (non-sandboxed) D-Bus client that runs `CreateSession`, `GetZones`, `SetPointerBarriers`, `ConnectToEIS`, `Enable`, waits for `Activated` |
| Helpers | [`probes/uinput_mouse.py`](probes/uinput_mouse.py) pushes the pointer to the barrier; [`probes/uinput_key.py`](probes/uinput_key.py) presses keys, to try to answer the dialog |

### Introspection (this machine)

`busctl --user introspect org.freedesktop.portal.Desktop /org/freedesktop/portal/desktop org.freedesktop.portal.InputCapture`:

- Interface `org.freedesktop.portal.InputCapture`, property `version` = 1, `SupportedCapabilities` = 15 (keyboard, pointer, touchscreen and one more bit).
- Methods: `CreateSession`, `GetZones`, `SetPointerBarriers`, `Enable`, `Disable`, `Release`, `ConnectToEIS`. Signals: `Activated`, `Deactivated`, `Disabled`, `ZonesChanged`.
- The same list also shows `CreateSession2` and `Start`, which are the newer replacement for `CreateSession`. Calling `CreateSession2` returns `UnknownMethod`: the frontend declares it, but this version does not implement it. Use `CreateSession` for now, and re-check when the portal frontend moves on (the portal marks `CreateSession` as deprecated).
- `/usr/share/xdg-desktop-portal/portals/gnome.portal` lists `org.freedesktop.impl.portal.InputCapture`, so the GNOME backend implements it.

### Live call

`CreateSession` on GNOME makes `xdg-desktop-portal-gnome` open a permission dialog (the journal shows `Failed to associate portal window with parent window`, which is what the backend logs when it shows a dialog for a caller without a window; the backend request object `/org/freedesktop/portal/desktop/request/.../probe...` stayed alive). No one was at the machine to answer. Three runs waited 60 s each and got no `Response`. Keys sent through `uinput` (Tab, Space, Enter) did not answer the dialog, so it needs a pointer click or focus that the probe could not give.

So these steps are **not verified on this machine**: `GetZones`, `SetPointerBarriers`, `ConnectToEIS` and the `Activated` signal. Run the probe again with someone at the screen (`python3 probes/t10_1_inputcapture.py --push`: it moves a uinput mouse into the right-edge barrier) before the input capture task (T12.2) ships.

lan-mouse is the existing open source program that uses this same portal on GNOME and KDE. It is evidence that the flow works in practice. It is not a test of UrDevice.

## Behaviour that affects the design

- **A dialog on every start on KDE.** Plasma shows "Input Capture Requested" when a program asks to capture input, and keeps asking on every session. Reports say it cannot always tell which program asked and offers no remember option in Plasma 6.4 ([KDE forum](https://discuss.kde.org/t/input-capture-requested-but-for-what/29373)). Plasma 6.3 added portal pre-authorization (see spike T0.6), which may let an admin or the user skip it. Plan for one dialog each time the shared mouse is switched on.
- **A dialog on GNOME.** The GNOME backend shows one at `CreateSession`. The `InputCapture` API has no restore token (unlike RemoteDesktop in T0.6), so assume one dialog per session.
- **libei is the transport.** `ConnectToEIS` returns a file descriptor for an EIS socket. UrDevice reads libei events from it (pointer motion, buttons, keys) and forwards them as `KvmEnter` and input datagrams (§18.3). `libei1` 1.5.0 is installed on this machine.
- **Barriers are in portal zone coordinates.** `GetZones` returns the layout and a `zone_set` number. `SetPointerBarriers` takes that `zone_set`, so barriers must be set again after `ZonesChanged` (from the portal's API; not exercised here).

## Decision for the implementation tasks (T12.2, T12.3)

1. Use `InputCapture` with libei on GNOME 45+ and KDE Plasma 6.1+. Detect support by reading the `version` property at runtime; if the interface is missing, show "this desktop cannot share its mouse" and still allow being controlled (§18.3 already says so).
2. Do not add a layer-shell fallback for wlroots in Release 2. Revisit if users ask.
3. The Linux shared mouse needs the UrDevice dialog plus the desktop dialog on each start. Tell the user in the UI that the desktop will ask.
4. Use the `CreateSession` call now. Add `CreateSession2` and `Start` when the installed portal implements them.
5. Add a manual test at T12.3 with someone at the machine: barrier, `Activated`, `Release` with the cursor position hint, and the escape hotkey (R19.4).

## Risks

| Risk | Plan |
|---|---|
| GNOME capture end to end is untested here (to verify in final device pass) | Run `probes/t10_1_inputcapture.py --push` with the dialog answered, before T12.2 starts |
| KDE untested here (to verify in final device pass) | Test on Plasma 6.1 or newer before the Release 2 candidate |
| Keys captured by libei on the sender stop reaching the local desktop. If UrDevice hangs, the user is locked out | Keep the escape hotkey (R19.4) in the capture layer, release on any error, and release when the peer disconnects |
| Portal API still moving (`CreateSession2`) | Wrap the portal calls behind one module |
| The KDE dialog may not name the program (reported for Synergy 3) | Ship a desktop file with the app name, and check how the dialog shows it when KDE is tested |
