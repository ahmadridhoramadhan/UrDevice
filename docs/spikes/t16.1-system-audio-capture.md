# Spike T16.1: capturing system audio on each OS

Date: 20 November 2026. This spike is task T16.1 of the speaker feature (R31, issue #40). It was done with the Release 2 spikes (issue #25) and does not close #40.

Result: **Linux works** (PipeWire monitor source, checked here). **Windows, macOS and Android have a documented API for it**; the probes for Windows and Android are written but were not run in this pass, so those rows say "to verify in final device pass". macOS was never testable here (no Mac).

## Question

R31.1 wants any host (Windows, macOS, Linux, Android) to send its system audio to another device. R31.7 says that where an OS cannot capture, the UI must say so and explain what to enable. Which OS and version can capture, and what does the user have to approve?

## Results by OS

| OS | API | Needs from the user | Status |
|---|---|---|---|
| Linux (PipeWire or PulseAudio) | The `.monitor` source of an output | None | Tested here |
| Windows 10 and 11 | WASAPI loopback (`AUDCLNT_STREAMFLAGS_LOOPBACK` on the render endpoint) | None | Probe written. To verify in final device pass |
| macOS 13 and later | ScreenCaptureKit with `capturesAudio` | Screen Recording permission | Research. Untested (no device) |
| macOS 14.2 and later | Core Audio process tap (`AudioHardwareCreateProcessTap`) | Audio recording permission prompt | Research. Untested (no device) |
| Android 10 (API 29) and later | `AudioPlaybackCapture` with a `MediaProjection` | The system screen-capture consent dialog, plus `RECORD_AUDIO` | Probe written. To verify in final device pass |

### Linux (tested)

| Item | Value |
|---|---|
| Machine | Ubuntu, PulseAudio compatibility layer on PipeWire 1.6.2 |
| Sources found | `alsa_output.pci-0000_30_00.6.analog-stereo.monitor` and `alsa_output.pci-0000_30_00.1.hdmi-stereo.monitor` (s32le, 2 channels, 48 kHz). One per output device |
| Capture | `parec -d <default sink>.monitor --format=s16le --rate=48000 --channels=2` for 3 s returned 196,608 bytes. The test did not play any sound, so whether the data was non-silent was not checked |

Notes for the adapter:

- The default output's monitor is the source to read. When the user changes the default output, follow it (PipeWire emits metadata changes). Capturing one monitor misses audio sent to a different output.
- Use `libpipewire` through `pipewire-rs` (a stream with `PW_KEY_STREAM_CAPTURE_SINK` set to capture a sink's output), or the PulseAudio API as the fallback on systems without PipeWire. Both need no permission dialog for a normal desktop user. A sandboxed build would need the PipeWire portal; not tested.

### Windows (probe written, not run in this pass)

- [`probes/t16_1_wasapi_loopback.cpp`](probes/t16_1_wasapi_loopback.cpp): opens the default render endpoint, initializes `IAudioClient` in shared mode with the loopback flag, and prints frame counts and peak level every 500 ms. Run it while any app plays sound, and again with nothing playing.
- Known behaviour to check: loopback delivers no packets while nothing plays, so the sender must fill silence or send nothing. The mix format is float32, so convert to 16-bit or encode directly to Opus.
- Windows 10 build 20348 and Windows 11 can also capture one process's audio (process loopback through `ActivateAudioInterfaceAsync`). Not needed for R31, which wants all system audio.
- To verify in final device pass: build the probe with MSVC, run it on Windows 11 build 26200, record the mix format and whether silence produces zero frames.

### macOS (research, untested)

- ScreenCaptureKit (macOS 13 and later) can deliver system audio buffers with an `SCStream` and `capturesAudio = true`, under the standard Screen Recording permission ([sck-record notes](https://github.com/connerkward/macos-screen-recorder-system-audio); [overview of the two APIs](https://www.recall.ai/blog/how-to-get-access-to-system-audio)). It sets up a screen stream even for audio-only use, so use the smallest content filter and drop the video frames.
- Core Audio process taps (macOS 14.2 and later, `AudioHardwareCreateProcessTap`) capture audio without a screen stream, and need an audio recording permission ([Apple developer forum answer](https://developer.apple.com/forums/thread/718279)). This is the cleaner choice on macOS 14.2 and later.
- A loopback driver such as BlackHole needs the user to install a third-party audio driver and set it as output. Do not require it.
- A Sequoia beta forum report shows Screen Recording permission problems for audio capture ([forum](https://developer.apple.com/forums/thread/760112)). Retest on each macOS release.
- To verify in final device pass: needs a Mac. Mark "untested (no device)" in CI and in the UI until tested.

### Android (probe written, not run in this pass)

- `AudioPlaybackCapture` was added in Android 10. The app records what other apps play, through a `MediaProjection` token, which Android only grants after a user consent dialog ([Android docs: Capture video and audio playback](https://developer.android.com/media/platform/av-capture)).
- The capture service must run as a foreground service of type `mediaProjection`, with `RECORD_AUDIO` granted.
- Only audio with usage `MEDIA`, `GAME` or `UNKNOWN` can be captured. Other apps can opt out: apps that target Android 10 or later are capturable by default, and apps below that must opt in ([API reference](https://developer.android.com/reference/kotlin/android/media/AudioPlaybackCaptureConfiguration.html)). Phone calls, system sounds and DRM-protected audio are not captured. The UI must say this (R31.7).
- The consent dialog has to appear on each start (Android 14 and later also limits reusing one token). That fits the Always Ask model of R31.3, but "allow" mode on a phone host still needs one tap on the phone the first time and after each stop.
- [`probes/android_apc/`](probes/android_apc/) is a small standalone app (plain Java, built with `build.sh` using the SDK tools, not Gradle) that records for 12 s and logs the peak level every 500 ms. To verify in final device pass: vivo I2505, Android 16: record the peak level while music plays.

## Decision for the implementation tasks (T16.2 to T16.4)

1. **Linux host:** read the default sink's monitor through PipeWire, with a PulseAudio fallback. Capture stereo 48 kHz, encode to Opus.
2. **Windows host:** WASAPI shared-mode loopback on the default render endpoint, float32 to Opus. No driver needed, no signing.
3. **macOS host:** Core Audio process tap on 14.2 and later; ScreenCaptureKit audio on 13 to 14.1. Behind "untested" until a Mac is available.
4. **Android host:** `AudioPlaybackCapture` with a foreground service. Show what is not captured. A phone is mostly a target, so this is lower priority.
5. Where capture is impossible (macOS before 13, a refused permission), show the reason and the step the user must take (R31.7).
6. The audio protocol (T16.2) should expect the sender to produce nothing during silence on Windows.

## Risks

| Risk | Plan |
|---|---|
| Windows and Android results are not measured yet | Run the two probes in the final device pass and update this page |
| macOS untested | Test before it is offered as supported |
| Capturing "everything the computer plays" can leak private audio (calls, notifications) | The speaker is a watched capability: indicator and Stop button on the host (R31.5), and it needs the target's own permission setting (R31.3) |
| Different outputs on Linux (HDMI vs headphones) | Follow the default sink; test switching during a stream (T16.3) |
