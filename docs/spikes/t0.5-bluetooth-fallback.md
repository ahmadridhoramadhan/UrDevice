# Spike T0.5: Bluetooth PAN and BLE fallback

Date: 19 November 2026. Result: **PAN works between Android and Linux** with today's core, through a reconnect. **BLE between macOS and Android is not tested yet**, because no Mac is available. It will be done last, with the macOS checks in #52.

## PAN test setup

| | Device |
|---|---|
| Desktop | Ubuntu (GNOME), BlueZ, NetworkManager, wired Ethernet `192.168.18.13` |
| Phone | vivo I2505, Android 16, Wi-Fi `192.168.18.23`, Bluetooth name "iQOO Z10R 5G" |
| Core | `main` at `68a3c19` (after PR #53), a headless peer on the laptop and the debug app on the phone |
| PAN | Phone: Settings → Hotspot → Other hotspot settings → Bluetooth tethering. Laptop: NetworkManager "Network" connection, with `never-default` so the laptop kept its wired internet and used no mobile data |

Steps:

1. Pair the laptop and the phone over Bluetooth. Both show the same passkey. The phone's "allow access to contacts and call history" box was turned off; UrDevice does not need it.
2. Turn on Bluetooth tethering. The laptop got `10.124.64.208` and the phone `10.124.64.53`.
3. Pair UrDevice by code over Wi-Fi.
4. Turn off the phone's Wi-Fi, wait, turn it on again.
5. Turn off PAN on the laptop.

## Results

| Event | What happened | Time |
|---|---|---|
| PAN up | ICMP over PAN: 10 of 10 replies, 24–92 ms, average 59 ms | |
| Session on Wi-Fi | RTT 10–11 ms | |
| Phone Wi-Fi off | The session stayed "Connected" until QUIC's idle timeout ended it | about 32 s |
| Reconnect over PAN | The connector found the phone's PAN address from its UDP announcement and connected. No new pairing | 1.5 s after the session closed |
| Session on PAN | RTT 65–83 ms (quinn's smoothed RTT) | |
| Phone Wi-Fi back on | The session stayed on PAN. It did **not** move back to Wi-Fi | 60 s watched |
| PAN off on the laptop | Idle timeout again, then a reconnect over Wi-Fi | about 36 s, then 0.5 s |

The session uses the same mutual-TLS QUIC connection with pinned keys on both paths (R6.3). Nothing about the PAN path is plain text.

## What this means for #23

The design in §8.1 works, but three parts are still missing:

1. **Loss is found too late.** A dead path is only noticed when the 30 s idle timeout fires. R6.1 asks for a move to PAN, and a presentation can't wait 30 s. Fix: watch the interfaces (`if-watch`, as §8.1 says) and send a probe when the LAN interface goes away; also lower the timeout for a path that has stopped answering, for example 3 missed keep-alives.
2. **No move back to the LAN.** R6.5 asks for a move back within 10 s. Today the session stays on PAN until PAN breaks. Fix: when a LAN address of the peer shows up again (announcement or interface change), open a new connection on it and close the PAN one, or use QUIC migration.
3. **The path label is wrong.** The snapshot always reports `wifi`, so the chip shows Wi-Fi while running over PAN. R4.8 and R6.4 need it to say Bluetooth. Fix: set the path from the interface of the local address (`bnep*`, `bt-pan`, `enx…` for a Bluetooth adapter on NetworkManager).

Other notes:

- NetworkManager names the PAN interface after the Bluetooth adapter's MAC (`enxe848b8c82000` here), not `bnep0`. Don't detect PAN by interface name alone; ask NetworkManager or check the device type.
- If the laptop has no other internet, PAN makes it use the phone's mobile data. The app should not make PAN the default route. This phone also has a 200 MB one-time limit for tethering.
- Android does not let an app turn on Bluetooth tethering, so the app opens the hotspot settings screen (R6.6). On this vivo phone the switch is under "Other hotspot settings".
