# Spike T10.3: virtual displays (GNOME, KDE, Windows, macOS)

Date: 20 November 2026. Result: **GNOME works** (tested here, through Mutter's own ScreenCast API; the portal path was not completed). **KDE Plasma is supported by the same portal source type** (research from other projects; not tested). **Windows needs a signed IddCx driver**, which needs an EV certificate and a registered company, so it is the costly path. **macOS `CGVirtualDisplay`** is a private API that other apps use today, with no test here.

## Question

R20.2 wants the phone to act as a second display. Which OS can create a display that has no monitor behind it, with what setup, and at what cost?

## What was tried

### GNOME on Wayland (this machine)

| Item | Value |
|---|---|
| Machine | Ubuntu, GNOME Shell 50.1, Wayland, one 1920x1080 monitor (`HDMI-1`), PipeWire |
| Probe 1 | [`probes/t10_3_virtual_screencast.py`](probes/t10_3_virtual_screencast.py): XDG ScreenCast portal with `types` = 4 (virtual) |
| Probe 2 | [`probes/t10_3_mutter_virtual.py`](probes/t10_3_mutter_virtual.py): `org.gnome.Mutter.ScreenCast` `RecordVirtual`, plus a `gst-launch-1.0 pipewiresrc` consumer, plus `org.gnome.Mutter.DisplayConfig.GetCurrentState` before, during and after |

Portal (probe 1):

| Check | Result |
|---|---|
| ScreenCast portal | version 5; `AvailableSourceTypes` = 7, which includes virtual (4) |
| `CreateSession` and `SelectSources` with `types` = 4 | Accepted (`Response` 0) |
| `Start` | Blocked 50 s on the portal's permission dialog that no one answered. The virtual monitor from the portal path was therefore not seen |

Mutter's own API (probe 2), which needs no dialog for a non-sandboxed caller:

| Step | Result |
|---|---|
| `CreateSession`, `RecordVirtual`, `Start` | All succeeded. `PipeWireStreamAdded` gave a node (99 in the runs). The node is `Stream/Output/Video` from `gnome-shell`, `meta-screen-cast-src`, BGRx and BGRA, default 1280x720, width and height range 1 to 16384 |
| Monitors with no consumer connected | Unchanged: only `HDMI-1`. The virtual monitor does not exist until a client connects to the stream |
| Monitors with a consumer connected (asked for 1024x768) | A second logical monitor `Meta-0` appeared at x=1920, current mode 1024x768 at 60 Hz, scale 1.0, right of the real monitor |
| After `Stop` | `Meta-0` disappeared. Only `HDMI-1` remained. No leftovers |

So on GNOME the second display's size is set by the consumer. UrDevice asks for the Android device's native resolution (design §18.4), and Mutter makes a monitor of that size. Windows can be dragged onto it like any other monitor. Whether the monitor stays when the stream stops and restarts, and how it behaves with fractional scaling, were not tested.

The portal path is what a sandboxed or Flatpak app must use, and it was not completed because of the dialog. The Mutter interface is private to GNOME and could change, so UrDevice must use the portal as the main path and test it with someone at the screen.

### KDE Plasma (research, untested)

- KWin supports `ScreenCast` `SourceType` virtual and its own `zkde_screencast_unstable_v1` virtual output. Third-party projects that use it today: [Orbiscreen's desktop notes](https://github.com/shadow-x78/orbiscreen/blob/main/docs/DE_SUPPORT.md) say the monitor "appears when a client connects", needs no root, no kernel module and no share dialog on Plasma, and [a Sunshine setup](https://github.com/jhonsnake/sunshine-kde-virtual-display) streams a headless virtual monitor on Plasma 6.
- Those are third-party claims. They match the GNOME behaviour above (the monitor lives while the stream is connected), but UrDevice has not run on KDE.

### Windows: Indirect Display Driver (IddCx), research only

An IddCx driver is a user-mode (UMDF) driver that adds a monitor. A virtual display cannot be done without a driver on Windows. Signing facts from Microsoft's documentation ([Register for the Hardware Developer Program](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/hardware-program-register), [Driver code signing requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs)):

- Releasing a driver that loads on a normal PC means attestation signing through the Partner Center hardware dashboard.
- To register the dashboard account you must have an **EV code-signing certificate**. The certificate is needed for registration, not for signing the driver itself.
- Registration needs a Microsoft Entra ID global administrator, a company record (a D-U-N-S number or manual company details), a legal contact who can sign agreements, and answering a business questionnaire. That is a company, not an individual's account.
- Cost: an EV certificate from a certificate authority. A Microsoft Q&A post quotes about $300 a year ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5866910/hardware-program-verification-using-azures-trusted)); prices vary by authority. The attestation submission itself is free.
- Development without signing: Windows test-signing mode lets a test-signed driver load, but it needs Secure Boot off and shows a watermark, so it is for developers only.
- That Q&A post asks whether Azure Trusted Signing can replace the EV certificate for registration. The documentation above still says EV is required, so plan for EV.

Not tested here: building a sample IddCx driver. The build needs the WDK, which is not on the Windows test machine. The value of testing it here is low, because it would load only with test-signing on, which changes the laptop's security settings. Decide on the signing path first.

### macOS: `CGVirtualDisplay` (research, untested)

- `CGVirtualDisplay` is private CoreGraphics API. DeskPad, BetterDisplay-style apps and several open source tools use it. DeskPad's README says it is "not suitable for Mac App Store distribution" ([DeskPad fork](https://github.com/thomasdye12/DeskPad)).
- BetterDisplay's maintainer reports that the app "mostly works" on macOS Tahoe beta 1 ([discussion](https://github.com/waydabber/BetterDisplay/discussions/4418)), which suggests the API still exists on macOS 26.
- Apple can change or remove it in any release (design §18.16 already flags this). No Mac was available to test.

## Decision for the implementation task (T12.4)

| OS | Back-end | Release 2 plan |
|---|---|---|
| Linux GNOME and KDE | ScreenCast portal `SourceType` virtual. The consumer asks for the Android device's native size. Start with `persist_mode` and a restore token as in T0.6 | Ship. Test GNOME with the dialog answered and KDE on Plasma 6, before the candidate |
| Windows 11 | IddCx driver | Do not ship in the first Release 2 candidate unless an EV certificate and company account exist. Show "not available" meanwhile. Decide on the certificate before work starts |
| macOS | `CGVirtualDisplay` behind a feature flag | Optional. Ship off by default, retest on each macOS release. Not allowed in a Mac App Store build |
| Windows 10 and older, wlroots, X11 | None | "Not available" in the UI. A mirror of an existing monitor (screen share) stays possible |

Design §18.4 stays as written. One note to add to the Windows row: the account needs a company record, not only the certificate.

## Risks

| Risk | Plan |
|---|---|
| Portal permission dialog was not answered, so the portal virtual path is unverified here (to verify in final device pass) | Re-run `probes/t10_3_virtual_screencast.py` with someone at the screen (answer the dialog, pick a monitor type) before T12.4 starts |
| Virtual monitor exists only while a consumer is connected | Fine for a stream. UrDevice must treat "no monitor" as "stream not started" and not move windows back itself |
| IddCx signing needs a registered company and certificate | The owner decides. Until then Windows has no second display |
| `CGVirtualDisplay` can break on any macOS update | Feature flag, version check at runtime, clean "not available" |
| A virtual display exposes the whole desktop of its windows to the phone | The indicator and Stop button apply (R5.4), as for screen sharing |
