# Spike T0.4: AccessibilityService and Google Play

Date: 19 November 2026. Result: **#19 can ship on Google Play as designed, with conditions.** Play does not ban the API for apps that are not accessibility tools. It asks for a declaration, a separate in-app disclosure, and user consent. Approval is not guaranteed.

## Decision

- Remote control of the phone (R9.3) uses `AccessibilityService.dispatchGesture()` for taps and swipes. Keep this design.
- Do **not** set `isAccessibilityTool="true"`. UrDevice is not built mainly for people with disabilities. A false claim gets the app rejected and blocked by Play Protect.
- The service only dispatches gestures. It does not read window content, so `canRetrieveWindowContent` stays `false`.
- Keep the R5 rules in every build: Remote control defaults to Always Ask, the phone shows an indicator and a Stop button, and nothing runs unattended.
- For the hackathon the APK is installed from GitHub. Play comes later and needs the steps in "Before a Play release".

## Policy rules that apply

| Rule | What it means for UrDevice | Source |
|---|---|---|
| Apps that are not accessibility tools may use the API | Allowed, after review | [Play: Use of the AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) |
| Automation must have a narrow, clear purpose. Apps may not start, plan, and run actions on their own | Each gesture comes from the user on the paired desktop. No macros, no agent | same |
| Only apps whose main purpose is helping people with disabilities may set `isAccessibilityTool` | Leave it unset | same |
| Prominent disclosure: inside the app, in normal use, separate from other disclosures, says what is accessed and how it is used, needs a tap to agree | A dedicated screen before opening Accessibility settings | same, and [Play User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311?hl=en) |
| Apps targeting API 31+ with an AccessibilityService fill in a declaration in Play Console. A changed use needs a new declaration | Fill it in for the first Play release; update it if the service ever reads content | [Play: Use of the AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en) |
| Services that inject input declare `android:canPerformGestures="true"` | Needed for `dispatchGesture()` | [Android: AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) |

KDE Connect is on Play with the same use: its listing says the Accessibility permission is only for the Remote Input feature ([Play listing](https://play.google.com/store/apps/details?hl=en_US&id=org.kde.kdeconnect_tp)). This shows the pattern can pass review. It is not a promise.

## Limits on the phone

| Limit | Effect | Source |
|---|---|---|
| Restricted settings (Android 13+) for apps installed outside a store | The user must open the app's info page and allow restricted settings before turning on the service. The app explains this; it never tries to get around it | [Android Help](https://support.google.com/android/answer/12623953?hl=en) |
| Advanced Protection | Accessibility services are limited to verified accessibility tools, so remote control of the phone does not work while it is on. Show "Not available while Advanced Protection is on" | [Android Help: Advanced Protection](https://support.google.com/android/answer/16339980?hl=en) |
| Sensitive views (Android 16) | Views marked `accessibilityDataSensitive`, or with `filterTouchesWhenObscured`, refuse gestures from services that are not accessibility tools. Login and payment screens may ignore taps | [Android Developers blog](https://developer.android.com/blog/posts/enhancing-android-security-stop-malware-from-snooping-on-your-app-data) |
| Local network (Android 17, target SDK 37) | Local network access needs `ACCESS_LOCAL_NETWORK`. The manifest already declares it | [Android 17 announcement](https://android-developers.googleblog.com/2026/06/Android-17.html) |

## Disclosure plan

Show this screen right before the app opens Android's Accessibility settings. "Agree" opens the settings; "Not now" goes back, and the rest of the app keeps working. The text goes through `strings.xml`.

> **Let your paired computer control this phone?**
>
> UrDevice uses Android's Accessibility service to send taps and swipes to this phone while a remote-control session is running. A session starts only when you approve it on this phone. UrDevice does not use this service to read, record, or send what is on your screen. Commands come only from your paired devices over your local network. While a session runs, this phone shows who is in control and a Stop button. You can turn the service off at any time in Android settings.
>
> [Not now] [Agree]

The sentence about not reading the screen is only true while the service is gesture-only. If that changes, change the text, the Play declaration, and the privacy policy together.

## Before a Play release

1. Play Console declaration: not an accessibility tool; purpose "app functionality"; core feature: "The user controls their own paired phone from their own computer on the local network. Each session is approved on the phone, shows an indicator, and can be stopped on the phone."
2. Data safety and privacy policy: the service collects no screen data. Gesture commands travel only between the user's paired devices, end-to-end encrypted, with no server.
3. Review video: open the app, show the disclosure, tap "Not now" (feature stays off), open it again, tap "Agree", turn on the service, approve a session on the phone, send a few taps from the desktop, show the indicator, and press Stop.
4. Store listing: describe remote control as a feature for the user's own devices, and name the Accessibility permission and why it is needed.

## Changes to the spec

None. R5 (Always Ask, indicator, Stop) and R9.3 already match what Play asks for. When #19 is built, its task list should include the disclosure screen and the "restricted settings" and "Advanced Protection" messages above.
