# Spike T10.5: reading notifications on desktop hosts

Date: 20 November 2026. Result: **Windows 11 can read notifications from a plain unpackaged `.exe` by polling `UserNotificationListener`; the change event needs package identity.** **GNOME can be monitored over D-Bus with `BecomeMonitor` and no dialog.** KDE is research only. macOS stays unsupported (R18.1).

## Question

Design §18.2 says Windows needs package identity (MSIX or sparse package) and the user's consent, and Linux uses a D-Bus monitor. What does a desktop host need in practice?

## Windows 11 (tested)

| Item | Value |
|---|---|
| Machine | Windows 11 25H2, build 10.0.26200.9974, signed in as a normal user |
| Probe | [`probes/t10_5_unl.cpp`](probes/t10_5_unl.cpp) (C++/WinRT, built with MSVC Build Tools), helper [`probes/t10_5_toast.ps1`](probes/t10_5_toast.ps1) posts one test toast. The probe prints counts and text lengths only, never notification text |
| Consent state | `HKCU\...\CapabilityAccessManager\ConsentStore\userNotificationListener` = `Allow` on this machine. No per-app consent entry existed for the probe |

Unpackaged exe (no package identity; `GetCurrentPackageFullName` returned 15700, `APPMODEL_ERROR_NO_PACKAGE`):

| Check | Result |
|---|---|
| `UserNotificationListener::Current()` | Works |
| `GetAccessStatus()` and `RequestAccessAsync()` | Both `Allowed`. No prompt appeared |
| `GetNotificationsAsync(Toast)` | Works from an SSH session (session 0) and from the interactive desktop. 19 to 23 toasts listed over the runs |
| Reading text | `Notification().Visual().GetBinding(ToastGeneric)` returned the text elements |
| App name | `AppInfo().DisplayInfo().DisplayName()` and `AppUserModelId` work from the interactive desktop (for example "Google Chrome"). In the session 0 run `AppInfo()` failed with `0x80004001`, so run the reader inside the user's desktop session, which the app does anyway |
| New toast | After one test toast the list grew by one (22 to 23), so polling sees new notifications |
| `NotificationChanged` event | **Fails** with `0x80070490` (element not found), both in session 0 and in the interactive session |

Sparse package (a throwaway self-signed `UrDevice.Spike` MSIX with `userNotificationListener`, registered with an external location; the exe's manifest links it to the package):

| Check | Result |
|---|---|
| Package identity | Yes (`GetCurrentPackageFullName` returned 122, buffer too small, which means a name exists) |
| Listing toasts | Works, same as above |
| `NotificationChanged` subscribe | No error. In a 25 s run with one test toast after 7 s, no event arrived (0 events). A 40 s repeat was started but its result was not read before the session ended |
| Registration | `Add-AppxPackage` from the SSH session failed with `0x80070005` (access denied). It worked from an elevated interactive task. The package needs a trusted signing certificate, installed in `LocalMachine\TrustedPeople` for a self-signed one |

So with identity the event is accepted but not shown to work; without identity it fails. Neither path is needed for the first version, because polling works.

Cleanup: the sparse test package and its certificate are still registered on the Windows laptop (`UrDevice.Spike`, `CN=UrDevice Spike`). Remove with `D:\dev\sparse_remove.ps1` in the final device pass.

## Linux GNOME (tested)

| Item | Value |
|---|---|
| Machine | GNOME Shell 50.1, Wayland, session bus |
| Probe | [`probes/t10_5_notify_monitor.py`](probes/t10_5_notify_monitor.py): a private bus connection that calls `org.freedesktop.DBus.Monitoring.BecomeMonitor` with match rules for `org.freedesktop.Notifications.Notify` (also `org.gtk.Notifications` and `org.freedesktop.portal.Notification`) |
| `BecomeMonitor` as the logged-in user | Accepted. No dialog, no extra permission |
| A `Notify` call sent with `gdbus call` | Seen with sender, app name `probe-app`, summary, body, actions `['reply','Reply']`, hints, and replaces id |
| Other paths | The `org.gtk.Notifications` and portal rules were registered but no test notification used those paths. To verify in final device pass: a GTK app that uses `GNotification`, and a sandboxed app |

A normal user can already do this on the session bus, which is the same way `dbus-monitor` works. It reads the notification as sent, with no access to who dismissed it. A sandboxed UrDevice (Flatpak, Snap) is expected to be blocked from `BecomeMonitor`; not tested.

## KDE Plasma (research, untested)

Plasma's notification server also owns `org.freedesktop.Notifications`, and `BecomeMonitor` is a message bus feature, so the same probe should work. To verify in final device pass on a Plasma machine.

## macOS

No public API reads other apps' notifications. Not supported (R18.1); the UI says so.

## Decision for the implementation task (T11.1)

1. **Windows:** poll `GetNotificationsAsync(Toast)` about once a second while mirroring is on, and diff by notification id. Do not ship a sparse or MSIX package for this. No `NotificationChanged` event. Check `GetAccessStatus()` at start; if it is `Denied`, show "Allow notification access in Windows Settings" with a link to `ms-settings:privacy-notifications`.
2. **Linux:** `BecomeMonitor` with `zbus` on `org.freedesktop.Notifications.Notify`, as in design §18.2. Also add the `org.gtk.Notifications` rule if testing shows GTK apps use it.
3. Desktop hosts send text, title, app name and icon only, no actions (R18.4), unchanged.
4. Content never goes into logs (security.md). Windows reading has no per-app consent on this machine, so UrDevice's own per-host and per-app choices (R18.2) are the only gate. Say so in the settings text.

Design §18.2's Windows row ("needs package identity") is corrected in this PR.

## Risks

| Risk | Plan |
|---|---|
| Polling depends on behaviour Microsoft documents for packaged apps; unpackaged use may stop working in a Windows update | Detect failure at start and show "not available". Keep the sparse package route as a documented option. Re-test on each Windows 11 feature update |
| Other Windows versions (Windows 10 1709 to 22H2, Windows 11 22H2 to 24H2) not tested | To verify in final device pass if a second machine exists. The listener API exists from Windows 10 1709 |
| Notification text is sensitive | Filter by app on the host before sending (R18.2); never log text; receiver keeps it in memory only (R18.6) |
| Linux sandboxed builds cannot monitor | Document that the Flatpak and Snap builds do not offer desktop to Android mirroring |
| KDE and the GTK notification path untested | Test in the final device pass |
