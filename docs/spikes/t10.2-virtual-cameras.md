# Spike T10.2: virtual cameras (Linux, Windows 11, macOS)

Date: 20 November 2026. Result: **Linux works** (v4l2loopback, tested). **Windows 11 works** (`MFCreateVirtualCamera`, tested on build 26200), but needs a media source DLL registered in `HKLM` by an installer with admin rights. **macOS is research only** (no Mac available): use a Core Media I/O Camera Extension, which needs a signed and notarized app and user approval.

## Question

R17.2 wants the phone camera to appear as a webcam on the desktop. Which mechanism does each OS need, what does the user have to do once, and what can the app do without admin rights?

## What was tried

None of these tests ran inside a video-call app. The brief forbids running a browser on the shared machines, so each test reads frames back through the same API a call app would use. A call-app check remains for the implementation task (T11.4).

### Linux: `v4l2loopback` (this machine)

| Item | Value |
|---|---|
| Machine | Ubuntu, kernel 7.0.0-43-generic, `v4l2loopback-dkms` 0.15.3 (module 0.15.3) |
| State found | The module was already loaded: `/dev/video10`, card label `UDevice Camera`, `exclusive_caps=1`. It comes from `/etc/modprobe.d/udevice.conf` and `/etc/modules-load.d/udevice.conf`, so it loads at boot. Mode is `crw-rw-rw-`, so no root is needed to open the device |
| Writer | `ffmpeg -re -f lavfi -i testsrc=size=1280x720:rate=30 -pix_fmt yuyv422 -f v4l2 /dev/video10` (12 s) |
| Reader | A second `ffmpeg -f v4l2 -i /dev/video10 -frames:v 30` and a one-frame PNG grab |
| Sudo | `sudo` is not usable from this agent ("no new privileges"), so the module could not be loaded or changed here. Nothing in the test needed it |

Results:

| Check | Result |
|---|---|
| Reader opened the device while the writer ran | Yes. 30 frames read, PNG of the 1280x720 test pattern saved |
| `v4l2-ctl --list-formats-ext` | One format: YUYV 1280x720 at 30 fps (the writer's format) |
| Device appears only while a writer is active | Yes. `exclusive_caps=1` makes it look like a plain capture camera, which is what Chrome and Zoom need |

Needs root once: `modprobe v4l2loopback devices=1 video_nr=10 card_label="UrDevice Camera" exclusive_caps=1`, plus a file in `/etc/modules-load.d` and `/etc/modprobe.d` to keep it across reboots. The module is built with DKMS, so Secure Boot machines need the DKMS key enrolled. A kernel with a newer API than the installed DKMS source can fail to build; the Ubuntu package follows the kernel, other distributions may lag.

### Windows 11: `MFCreateVirtualCamera`

| Item | Value |
|---|---|
| Machine | Windows 11 25H2, build 10.0.26200.9974 |
| Media source | [smourier/VCamSample](https://github.com/smourier/VCamSample) `VCamSampleSource` (MIT), built unmodified with MSVC from the Build Tools and registered with `regsvr32` |
| Probe | [`probes/t10_2_mfvcam.cpp`](probes/t10_2_mfvcam.cpp): `MFCreateVirtualCamera` (software camera source, session lifetime, current-user access), `Start`, enumerate with `MFEnumDeviceSources`, activate, read frames with a source reader |

| Check | Result |
|---|---|
| `regsvr32` of the media source | Success. Wrote `HKLM\Software\Classes\CLSID\{3cad447d-...}\InprocServer32` |
| `MFCreateVirtualCamera` and `Start` | `hr=0x00000000` both |
| Enumeration | `UrDevice Probe Camera (Windows Virtual Camera)` listed next to the real `USB camera` |
| Frames | 1280x960 at 30 fps, RGB32. 30 frames read in 187 ms. The first frame (saved as BMP) shows the sample's colour test pattern with "Format: RGB32 (CPU)" |
| DLL under the user profile instead of `D:\dev` | Also worked (5 frames). The DLL there had SYSTEM and Administrators on its ACL, so the Frame Server service could read it. A DLL that SYSTEM cannot read would be expected to fail; that was not tested |
| `Remove` and `Shutdown` at the end | Clean exit; the camera disappears with the session |

Facts from Microsoft's documentation ([`MFCreateVirtualCamera`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-mfcreatevirtualcamera), [`MFVirtualCameraAccess`](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/ne-mfvirtualcamera-mfvirtualcameraaccess)):

- The API exists from Windows build 22000 (Windows 11). It does not exist on Windows 10, so Windows 10 hosts get "not available".
- `MFVirtualCameraAccess_AllUsers` needs administrator rights in the caller. `CurrentUser` access did not need elevation for the calling program in this test.
- The sample's author notes the media source cannot be registered under `HKCU`, only `HKLM`, because several processes load it ([VCamSample README](https://github.com/smourier/VCamSample)). That registration is the step that needs admin. The installer does it once; the app then calls `MFCreateVirtualCamera` as a normal user. In this test session, `IsInRole(Administrator)` printed `False` while `regsvr32` still wrote `HKLM`, so the SSH account may already have write access to that key. That was not investigated, and a normal user account should be assumed to need an installer with admin.
- The media source is a COM DLL loaded by the Frame Server, not by UrDevice. UrDevice must send frames to it (shared memory or a named pipe). The sample generates its own pattern; a real source must be written for UrDevice (C++ or Rust COM), which is the main cost on Windows.
- No driver and no signing certificate was involved. A COM DLL does not need an EV certificate; sign it with the same code-signing certificate as the installer so SmartScreen and antivirus do not flag it.

### macOS: Camera Extension (research, untested)

No Mac was available. From Apple's material ([WWDC22 "Create camera extensions with Core Media IO"](https://developer.apple.com/la/videos/play/wwdc2022/10022/)) and developer forum threads ([CMIO camera extension installation](https://developer.apple.com/forums/thread/736838)):

- A Core Media I/O Camera Extension is a system extension that replaces the old DAL plug-ins. It needs macOS 12.3 or later.
- It lives in the app bundle under `Contents/Library/SystemExtensions`, must be signed with a Developer ID certificate (paid Apple Developer account) and notarized, and the app activates it with `OSSystemExtensionRequest`. The user then approves it in System Settings. The forum reports "invalid signature" and "does not appear" errors when signing or the bundle layout is wrong.
- Apps that sandbox a camera extension use an App Group to receive frames from the main app. The sample projects (for example [harshanacz/macOS-virtual-camera](https://github.com/harshanacz/macOS-virtual-camera)) report that Zoom, Meet, Teams, FaceTime and OBS list it.

## Decision for the implementation task (T11.4)

| OS | Back-end | Setup the user sees |
|---|---|---|
| Linux | `v4l2loopback` device written with YUYV frames. Check for `/dev/video*` with card label `UrDevice Camera` (or any loopback device that is writable); if missing, show the exact `modprobe` and config commands and offer a one-time root helper | One root step (package plus module options), once |
| Windows 11 | Own media source COM DLL, registered by the installer in `HKLM`; app calls `MFCreateVirtualCamera` with `CurrentUser` access | Installer asks for admin once. No prompt afterwards |
| Windows 10 | None. UI says it needs Windows 11 | n/a |
| macOS | Camera Extension in the app bundle | System extension approval in System Settings. Needs a paid Apple Developer account for Developer ID signing and notarization |

Design §18.1 and the R17.2 wording stay valid. No spec change.

Hold back the macOS and Windows work from the first Release 2 candidate if signing is not ready; Linux and Android-to-desktop viewing do not depend on them.

## Risks

| Risk | Plan |
|---|---|
| Not tested in a real call app (to verify in final device pass) | Check Chrome, Teams and OBS on Linux and Windows during T11.4, with someone at the machine |
| Windows media source is new code in a COM DLL loaded by a system service | Keep it tiny (read frames from shared memory), no network code, fuzz the frame header, sign it |
| `v4l2loopback` builds with DKMS and breaks on Secure Boot or new kernels | Detect and explain; link to the distribution package. Consider PipeWire camera support later |
| macOS extension untested | Mark "untested (no device)" in CI; test before shipping |
| Camera is a privacy-sensitive output | The indicator and Stop button apply to the virtual camera too (security.md). The device appearing in other apps is not itself a permission |
