# Spike T10.4: Google Play policy for full-screen intents, SMS, and call permissions

Date: 20 November 2026. Result: **keep the `play` and `full` build split (R29.3)**. SMS and call-log permissions are restricted on Play. Full-screen intents are allowed in the `play` build, but not granted by default, so the ring screen needs a fallback. This spike is document research; no build was changed.

## Question

R25.1 and R25.2 want a full-screen message on a ringing phone. R29 wants SMS and call controls. Can the Play build carry them, and does the planned `full` build split (design §18.13, T11.6) still hold?

## Findings

### Full-screen intents (R25, Find my device)

| Fact | Source |
|---|---|
| On Android 14 (API 34) and later, `USE_FULL_SCREEN_INTENT` is a special app access permission, not granted at install | [Play Console Help: foreground service and full-screen intent requirements](https://support.google.com/googleplay/android-developer/answer/13392821) |
| Play lets only apps whose core function is alarms or phone/video calls have it enabled by default. Other apps may use it, but only after the user grants it | same page; effective for apps targeting Android 14+ from 22 January 2025 |
| An app that uses the permission completes a declaration in Play Console that says whether its core functionality is a permitted case | same page |
| `NotificationManager.canUseFullScreenIntent()` tells whether the app has the permission (API 34+). If it is denied, the notification appears as an expanded heads-up notification on the lock screen. The app sends the user to `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` to grant it | [Android reference: NotificationManager](https://developer.android.com/reference/android/app/NotificationManager) |

UrDevice is not an alarm clock or a phone app, so **do not declare the core-function case**. A false declaration risks removal. Instead, declare the permission without claiming automatic grant, and let the user grant it. The existing design already falls back to a high-priority notification (§18.9). Add one step: when Find my device is first turned on, check `canUseFullScreenIntent()` and, if false, show a one-time prompt that opens the system screen. The ring itself uses the alarm audio stream, which does not depend on this permission, so the phone still rings at full volume without it. Only the full-screen message degrades to a heads-up notification.

### SMS and call log (R29)

Policy: [Use of SMS or Call Log permission groups](https://support.google.com/googleplay/android-developer/answer/10208820).

- Play restricts `READ_SMS`, `RECEIVE_SMS`, `SEND_SMS`, `RECEIVE_MMS`, `RECEIVE_WAP_PUSH`, `WRITE_SMS`, and the call log group (`READ_CALL_LOG`, `WRITE_CALL_LOG`, `PROCESS_OUTGOING_CALLS`). An app that does not qualify must remove them from its manifest. A qualifying app fills in a permissions declaration in Play Console, and apps without one may be removed.
- Permitted use is being the default SMS, Phone, or Assistant handler. UrDevice should not be the default SMS app: it relays messages and does not replace the user's messaging app.
- Play may give a **temporary exception** to apps that are not the default handler, when the permission is core to the app and no alternative exists. The list includes "Connected device companion apps that enable sending/receiving of SMS or calls" and "Cross-device synchronization or transfer of SMS or calls (such as between phone and laptop)", with `READ_SMS`, `RECEIVE_SMS`, `SEND_SMS` and `READ_CALL_LOG` as eligible permissions. "Device automation" is also on the list.
- So a Play listing for UrDevice's SMS relay is possible in principle, but it is a temporary exception, subject to review, and UrDevice's core function (a set of device-sharing tools) may not be accepted as an app whose critical core functionality is SMS. Do not plan on it.
- A page note says account verification by call will no longer justify `READ_CALL_LOG` from 27 January 2027. This does not affect UrDevice.
- `ANSWER_PHONE_CALLS` is a runtime ("dangerous") permission ([Android reference](https://developer.android.com/reference/android/Manifest.permission)). It does not appear in the SMS and call log policy list above. UrDevice's answer, decline and silence actions need `ANSWER_PHONE_CALLS` and `READ_PHONE_STATE` but no call-log permission. I found no Play Console declaration for those two in the pages read. Play review can still object, so list both in the store review notes.
- Android 14 also asks for a foreground service type. The Play help page lists `remoteMessaging` ("relay text communication to another device") as a type; UrDevice's existing `connectedDevice` service does not change.

## Confirm the flavor split

| Flavor | SMS and call permissions | Where it is distributed |
|---|---|---|
| `play` | None. No `READ_SMS`, `SEND_SMS`, `RECEIVE_SMS`, `READ_PHONE_STATE`, `ANSWER_PHONE_CALLS` in the manifest | Google Play (later; the hackathon build comes from GitHub) |
| `full` | `READ_SMS`, `SEND_SMS`, `RECEIVE_SMS`, `READ_PHONE_STATE`, `ANSWER_PHONE_CALLS` (as design §18.13) | GitHub Releases, F-Droid |

The split in R29.3 and design §18.13 is confirmed. The `play` build offers replies to messaging apps through notification mirroring (R18.4).

Rules for T11.6, so the `play` build cannot carry a restricted permission by accident:

1. Put the five permissions and the SMS and call code in a `full` source set only. The `main` and `play` source sets must not reference them.
2. Add a CI check that fails if the merged `play` manifest contains any of the restricted names. A manifest merge from a library could add one, so check the merged result of `processPlayReleaseManifest`, not only the source file.
3. The core's `telephony.v1` capability stays in both builds, but the `play` Android host reports "not supported in this build" and the desktop UI shows that.
4. Keep `USE_FULL_SCREEN_INTENT` in `main`. It is not restricted, only gated.

## Changes to the spec

None. R29.3 and design §18.13 already say what the spike confirms. One sentence is added to design §18.9 in this PR so T11.2 knows the permission is not granted by default.

## Risks

| Risk | Plan |
|---|---|
| Play changes these policies often (full-screen intent, SMS list) | Re-read the two policy pages when T11.6 starts and before the first Play submission |
| Play review treats the declaration for full-screen intent as unjustified | Do not claim core-function status. The notification fallback keeps Find my device working |
| `full` build users get no Play update channel | Document install steps. Offer F-Droid. Show the version in the app |
| A library adds a restricted permission to the `play` manifest | CI check on the merged manifest (rule 2) |
